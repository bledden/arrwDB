## The Recall Problem

### Why recall@10 = 1.0 at 10K but 0.464 at 1M

The HNSW fixes are correct (proven by 10K test), but recall degrades at 1M scale because:

1. **Random 1024-dim vectors are the worst case for HNSW.** In high dimensions, all vectors become roughly equidistant (curse of dimensionality). The graph structure can't form meaningful neighborhoods.

2. **Adaptive ef_search scales to 2000 at 1M** (from base 500 x4), but this only explores ~0.002% of the graph. At 10K, ef=500 explores ~5% - a 2500x better ratio.

3. **This is NOT an HNSW bug.** M=48 with proper paper algorithms is standard. The issue is fundamental to random high-dimensional data.

### Comparison: v1 vs v2

|--------|-------------------|-------------------|
| Recall@10 | 0.449 | 0.464 |
| Insert rate | 7.0 vec/s | 2.4 vec/s |

The fixes improved recall slightly (0.449 -> 0.464) but insert throughput dropped 3x due to the heuristic neighbor selection doing more work per insert.

### Next Steps for Recall

1. **Use real embeddings instead of random vectors.** Real text/image embeddings have meaningful cluster structure. HNSW with M=48 typically achieves >0.95 recall on real data. Random 1024-dim vectors are an unrealistically hard benchmark.

2. **If random recall still matters**, options:
   - Increase M to 64+ (denser graph, more memory)
   - More aggressive ef_search scaling (e.g., `sqrt(size/1000)` instead of `1 + log10(size/1000)`)
   - Reduce dimensions (random 128-dim would be much easier)

3. **NV-Embed-v2 integration** (from previous session planning) - switching from Cohere to NVIDIA's NV-Embed-v2 model (4096 dims, CC-BY-NC-4.0). NGC API key is in the 311ML project. This is the user's preferred embedding model.
